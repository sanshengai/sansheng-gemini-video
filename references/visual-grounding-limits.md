# 视觉定位(spatial grounding)能力边界 + 分辨率/帧率指引

> 本文件记录 gemini-3.5-flash 在本 skill 用法下的**视觉感知能力边界**,是引擎自身的客观事实(不绑任何上层业务)。
> 任何用本 skill 做"坐标定位 / 读屏幕小字 / 逐操作时间点"的调用方(直接用,或从你自己的代码调用)都该先读这一页。

---

## 1. 坐标(bounding box):区域级准,像素级不准 ⚠️

**实测结论(2026-06-03,真录屏样本)**:让 Gemini 返回元素的归一化包围框 `[ymin, xmin, ymax, xmax]`(0-1000),它能**正确指出"在画面哪一块"(左/右/上/下、哪个面板)**,但**像素级有偏差**——实测一个 API key 文本框,Gemini 给的纵向坐标偏了约 100px(≈画面高度 10%),按它的框直接打码**没盖住目标**。

**含义(硬规则)**:
- ✅ 坐标可用于:**粗定位 / 圈出大致区域 / 判断"敏感信息在右侧面板还是左侧列表"**。
- ❌ 坐标**不可用于**:**精确自动打码 / 像素级裁剪**。盲信坐标自动打码会漏(实测就漏了)。

**精确定位的正确流程(打码/裁剪必走)**:
```
Gemini 给「何时出现 + 在哪一块」(粗)
   → ffmpeg 抽该时间段的首/尾帧成图
   → 人(Claude)Read 那张帧,看准像素位置(精)
   → 再按精确坐标 + 时间段做处理
```
位置固定的敏感信息(key / 卡号 / 邮箱通常固定在某个面板的某一行),**抽一次帧、核一次像素就锁死**,后续同位置复用。这一步**省不掉**,是定位可靠性的兜底。

> 教训来源:一次录屏分析里想直接拿 Gemini 坐标给屏幕上的 key 自动打码,先做 demo 验证发现框偏了、没盖住目标 —— 差点漏泄露。**结论:坐标→自动处理这条路必须先 demo 验证,别乐观下结论。**

---

## 2. media_resolution:默认 low 省钱,但读小字/密钥要 high

视频 token = 帧数(fps × 时长)× 每帧 token(media_resolution 定)。默认 `low` 省 token,**但**:

| 场景 | 用哪档 | 实测依据 |
|---|---|---|
| 看懂操作流程 / 画面在干啥 | `low` 够 | 10 段教程录屏 low 全看懂,每段几分钱 |
| **逐字读密钥前缀 / 卡号 / 屏幕小字 / 精确 UI 文字** | **必须 `high`** | low 读不出 key 是 `AQ.` 还是 `AIza` 开头(差一个字就是计费来源不同),high 才坐实 |
| low 结果里关键文字标了"模糊/看不清" | 对该段/该时间窗 **`high` 复看** | -- |

`high` 成本仍低(单段几分钱),**凡是判断结果依赖"屏幕上那行字到底写了啥"的,直接上 high,别用 low 猜**。

---

## 3. fps:逐操作时间点要 ≥1.0,粗看用 0.2-0.5

| 目的 | fps | 说明 |
|---|---|---|
| 整体理解 / 验收 / 省 token | 0.2-0.5 | 录屏节奏慢,够用 |
| **逐次点击 / 逐操作的时间点** | **≥1.0** | fps 0.5 = 每 2 秒一帧,**快速连点会漏**;要逐点击时间轴必须 ≥1.0 |
| 强运动实拍 | 1.0+ | 低帧会丢运动信息 |

时间点精度本身受 fps 限制:fps 1.0 → 时间点精度约 ±1 秒,够**粗剪定位**,不到逐帧级。

## 4. 给调用方的提示

- 要"结构化的剪辑分析(点击/敏感信息/节奏)",用 `--prompt <指令> --schema <schema.json>` 驱动本 skill——**分析什么由你定义,本 skill 只负责看**。
- 凡涉及"坐标→处理(打码/裁剪)",必须按上面 §1 的流程加一道**抽帧人工核像素**,不能直接信本 skill 返回的 box 做自动处理。
